# ADR-013 — Internationalization Architecture

> **Status:** ✅ Accepted
> **Date:** 2026-05-12
> **Deciders:** Architecture Agent
> **Supersedes:** —
> **Affects:** `packages/i18n/`, `packages/web/lib/i18n/`, `scripts/validate-i18n.ts`

---

## Context

Narrare needs internationalization (i18n) for the frontend (and later CLI, MCP, and A2A interfaces). Three locales are supported: English (en, default), German (de), and French (fr). The framework chosen is next-intl, which integrates with Next.js App Router via `useTranslations()`.

Translation files were initially stored in `packages/web/messages/` as monolithic JSONs (`en.json`, `de.json`, `fr.json`). As the number of translation keys grew, the monolithic files became difficult to maintain and review — a single change to editor strings required editing a file that also contained auth, dashboard, wizard, settings, and error strings.

---

## Decision Drivers

- **Maintainability:** Large monolithic JSON files are hard to review in PRs and easy to merge-conflict
- **Discoverability:** Developers need to quickly find which file holds the string they want to change
- **Multi-consumer readiness:** Translations will eventually be consumed by Python services (CLI, MCP, A2A), not just the Next.js frontend
- **Validation:** Need automated checks for missing keys and broken placeholders across locales
- **Framework fit:** Solution must work cleanly with next-intl and Next.js App Router

---

## Options Considered

### Option A — Monolithic JSON per locale (status quo)

Keep `packages/web/messages/{locale}.json` as single files.

**Pros:**
- No migration effort
- Simple file loading (one import per locale)

**Cons:**
- Files grow unbounded as features are added
- Merge conflicts increase with multiple contributors
- No logical grouping — finding a key means searching the entire file
- Frontend-only location blocks future Python consumers

### Option B — Namespace-based JSON per locale in `packages/i18n/`

Move to `packages/i18n/messages/{locale}/{namespace}.json` with 7 namespaces: common, auth, wizard, dashboard, editor, errors, settings.

**Pros:**
- Small, focused files easy to review and diff
- Namespace maps to feature area — immediate discoverability
- `packages/i18n/` is consumer-agnostic (works for both TypeScript and Python)
- Validation can check per-namespace completeness
- New features get their own namespace file without touching others

**Cons:**
- Migration required (split monolithic files, update loader)
- Frontend loader must merge namespace files into a single messages object

---

## Decision

**We choose Option B — namespace-based JSON files in `packages/i18n/messages/`.**

The namespace structure aligns with our feature domains (auth, wizard, editor, etc.) and keeps files small enough to review at a glance. Placing translations in `packages/i18n/` rather than `packages/web/` makes them the single source of truth for all consumers — frontend today, Python services (CLI, MCP, A2A) tomorrow.

---

## Rationale

The monolithic approach breaks down as the project grows. A 500-line `en.json` with no logical grouping makes it hard to answer "where is the save button string?" and produces unnecessary merge conflicts when two developers work on different features.

The namespace approach trades a one-time migration cost for ongoing maintainability. The 7 namespaces (common, auth, wizard, dashboard, editor, errors, settings) map directly to the application's feature areas, so developers can find the right file intuitively.

English (en) is the reference locale. All new keys are added to `en/` first, and the validation script (`scripts/validate-i18n.ts`) checks that every key in `en/` exists in `de/` and `fr/` with matching ICU placeholders.

The frontend loader (`packages/web/lib/i18n/request.ts`) reads all namespace JSONs for the active locale and merges them into a single flat messages object, so `useTranslations("editor")` continues to work without any component changes.

---

## Consequences

**Positive:**
- Translation files are small, domain-focused, and easy to review
- Single source of truth in `packages/i18n/messages/` — not locked to frontend
- Automated validation catches missing keys and mismatched placeholders in CI
- New namespaces can be added without touching existing files

**Negative / Tradeoffs:**
- Adding a new translation key requires editing 3 files (en, de, fr) — though the validation script catches omissions
- The frontend loader does a merge step at runtime (negligible performance impact)
- Adding a new locale requires creating 7 new files (one per namespace)

**Constraints introduced:**
- RULE-06 (one responsibility per file): each namespace file covers one feature area
- Validation enforced via `scripts/validate-i18n.ts` in pre-commit and CI

## Implementation Notes

### File structure

```
packages/i18n/messages/
├── en/          ← Reference locale
│   ├── common.json
│   ├── auth.json
│   ├── wizard.json
│   ├── dashboard.json
│   ├── editor.json
│   ├── errors.json
│   └── settings.json
├── de/          ← German (mirrors en/)
└── fr/          ← French (mirrors en/)
```

### Adding a new translation key

1. Add the key to `packages/i18n/messages/en/<namespace>.json`
2. Add the same key to `packages/i18n/messages/de/<namespace>.json`
3. Add the same key to `packages/i18n/messages/fr/<namespace>.json`
4. The validation script will catch missing keys in CI

### Adding a new namespace

1. Create the JSON file in each locale directory (`en/`, `de/`, `fr/`)
2. Update `packages/web/lib/i18n/request.ts` to include the new namespace in the merge

### Adding a new locale

1. Create a new directory under `packages/i18n/messages/` (e.g., `es/`)
2. Copy all 7 namespace files from `en/` as a starting point
3. Translate the values
4. Register the locale in `packages/web/lib/i18n/routing.ts`

### Validation

`scripts/validate-i18n.ts` runs four checks:
1. **Hardcoded strings in TSX** — AST-based detection of raw English text in components
2. **Hardcoded error strings in Python** — regex-based detection in backend code
3. **Key completeness** — every key in `en/` must exist in `de/` and `fr/`
4. **Placeholder consistency** — ICU variables (e.g., `{count}`) must match across locales

### Future: Python loader

When CLI, MCP, or A2A consumers arrive, `packages/i18n/narrare_i18n/` will become a Python package that reads the same JSON files from `packages/i18n/messages/`. This avoids duplicating translations across language ecosystems.
