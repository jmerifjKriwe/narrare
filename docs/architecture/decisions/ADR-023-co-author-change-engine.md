# ADR-023 — Co-Author Change Engine

> **Status:** ✅ Accepted
> **Date:** 2026-05-29
> **Deciders:** Architecture Specialist
> **Affects:** `core/writing/`, `apps/api/narrare/writing/`, `packages/web/`, WRITE-006

---

## Context

WRITE-006 (Co-Author Mode) introduces a new AI interaction model: track-changes-style
revision where the user selects a passage, the AI proposes improvements, and the user
accepts or rejects individual changes. This differs fundamentally from the existing
rewrite mode (WRITE-004), which streams complete replacement text without granular
diff visibility.

### Symptom

The existing rewrite pipeline (`core/writing/pipeline_rewrite.py`) streams revised text
as a monolithic block. The user sees the full replacement but cannot inspect what
specifically changed, why it changed, or selectively accept parts. It is all-or-nothing.

### Root Cause 1 (2× Why)

**Why can't users see individual changes?** → The rewrite pipeline streams plain text.
There is no diff computation between original and revised text — the pipeline was
designed for full-replacement semantics, not track-changes semantics.

**Why was diff never built?** → Diff computation is a separate concern from text
generation. The rewrite pipeline correctly delegates to LLM streaming and
post-processing. Adding diff logic would violate RULE-06 (one responsibility per file).
A dedicated change engine is needed.

### Root Cause 2

The LLM produces text, not structured change annotations. Asking the LLM to output
per-change XML/JSON adds complexity and reduces reliability (see Alternatives — Option B).
Computing the diff server-side from plain text is deterministic, testable, and
independent of LLM behavior.

### Root Cause 3

Per-change feedback (accept/reject) is a learning signal that must flow through the
existing `FeedbackService` (LEARN-001). No new feedback infrastructure is needed —
the existing `context: dict` parameter on feedback events carries change metadata
(focus area, change type, reasoning). Batching on "Done" avoids per-change network
calls while preserving granularity.

### Existing Assets

| Asset | Location | Reuse in Co-Author |
|-------|----------|--------------------|
| Rewrite pipeline | `core/writing/pipeline_rewrite.py` | Pattern for streaming + PromptContext construction |
| `stream_rewrite()` | `pipeline_rewrite.py` | SSE streaming pattern, chunk accumulation |

| SET-005 resolution cascade | `apps/api/narrare/settings/` | User-configurable max selection length |

## Decision Drivers

- **Granular control:** Writers must see exactly what changed and accept/reject individually
- **Deterministic diff:** Diff computation must be deterministic and testable — independent of LLM output format
- **Focus-area scoping:** AI only revises within user-selected focus areas (word choice, dialogue, description, etc.)
- **Learning integration:** Per-change accept/reject feeds back into Rejection Learning (LEARN-001)
- **Streaming UX:** Users see the revised text stream in real-time, then review the diff
- **RULE-06 compliance:** Diff engine is a pure-function module, separate from pipeline streaming
- **RULE-03 compliance:** Contracts defined before implementation

---

## Options Considered

### Option A+ — Server-side Diff via `difflib.SequenceMatcher` (CHOSEN)

**Description:** LLM produces revised text as plain text (same as rewrite mode).
Server computes diff via Python's `difflib.SequenceMatcher`. Change types are derived
from user-selected focus areas. Aggregate reasoning is generated by the LLM in a
single pass alongside the revised text.

**Pros:**
- Deterministic diff — same original + revised always produces same result
- No LLM output format constraints — LLM focuses on text quality, not XML structure
- `difflib` is stdlib — zero new dependencies
- Diff computation is pure Python — easily testable, fast, no I/O
- Change types derived from focus areas — no LLM classification needed
- Reuses existing streaming infrastructure (SSE, `connectSSE`)

**Cons:**
- Diff is line/word-level, not semantic — cannot distinguish "improved dialogue" from
  "fixed grammar" without focus-area mapping
- Requires sentence grouping post-processing for meaningful change units
- Aggregate reasoning (not per-change reasoning) — LLM explains overall revision, not each change

### Option B — Structured LLM Output (XML per change)

**Description:** LLM outputs structured XML with per-change annotations:
`<change type="dialogue" reason="More natural speech">old → new</change>`.

**Pros:**
- Per-change reasoning directly from LLM
- Semantic change classification built into output

**Cons:**
- **LLM reliability:** Complex XML output format increases hallucination risk.
  The LLM must simultaneously revise text AND wrap each change in correct XML.
  Missing closing tags, malformed attributes, and inconsistent nesting are common
  with complex structured output.
- **Streaming hostile:** Structured XML cannot be streamed incrementally — the user
  sees nothing until the full XML is parsed. This breaks the real-time UX.
- **Format coupling:** Diff format is coupled to LLM prompt engineering. Changing
  the diff display requires changing the prompt. Violates separation of concerns.
- **Error recovery:** Malformed XML requires retry or fallback — adds complexity.
  A plain-text approach has no format to break.
- **Verdict: REJECTED** — LLM reliability concerns with complex per-change XML outweigh
  the benefit of per-change reasoning.

### Option C — Client-side Diff

**Description:** LLM streams revised text. Frontend computes diff using a JavaScript
diff library (e.g., `diff-match-patch`).

**Pros:**
- Zero server-side diff computation
- No new backend module needed

**Cons:**
- **No change types:** Client-side diff produces insert/delete/replace operations,
  not semantic change types (dialogue improvement, show-don't-tell, etc.)
- **No reasoning:** The diff is purely textual — no AI-generated explanation for
  why a change was made
- **Inconsistent results:** Different browsers or diff algorithms may produce
  slightly different results. Server-side diff is deterministic.
- **Feedback gap:** Per-change feedback requires change metadata (type, focus area)
  that the frontend cannot derive from a textual diff alone
- **Verdict: REJECTED** — Client-side diff cannot provide change types or reasoning,
  which are core to the Co-Author UX.

### Option D — Sentence-level Streaming

**Description:** Process the selection sentence-by-sentence. For each sentence, make
a separate LLM call, stream the revision, compute diff immediately, send as individual
SSE event.

**Pros:**
- Per-sentence diff available immediately during streaming
- Progressive disclosure — user sees changes as they happen

**Cons:**
- **N× cost:** For N sentences, N LLM calls instead of 1. A 100-sentence selection
  means 100× the LLM cost and latency.
- **N× latency:** Even with parallelism, coordinating N concurrent streams adds
  significant latency and complexity.
- **Inconsistent quality:** Each sentence is revised in isolation without context
  from surrounding revised sentences. The revision lacks coherence — sentence 5
  may be revised differently depending on whether sentence 4 was already revised.
- **Complex implementation:** Sentence-level streaming with N concurrent LLM calls
  requires significant new infrastructure (batch management, result ordering,
  partial failure handling).
- **Verdict: REJECTED** — N× cost and quality degradation make this unviable for
  selections longer than a few sentences.

### Option E — Hardcoded Max Selection Length

**Description:** Fixed maximum of 2000 words, non-configurable.

**Pros:**
- Simpler implementation — no settings cascade integration

**Cons:**
- One-size-fits-all limit does not account for different LLM context windows
  or user preferences
- Violates the established SET-005 pattern for user-configurable limits
- Changing the limit requires a code change instead of a settings update
- **Verdict: REJECTED** — Less flexible than SET-005 pattern. The 3-layer resolution
  cascade (user → project → system default) already exists and should be reused.

## Decision

**We choose Option A+ — Server-side Diff via `difflib.SequenceMatcher`.**

### Specific Decisions

1. **Server-side Diff:** LLM produces revised text (plain), server computes diff via
   `difflib.SequenceMatcher`. Change types derived from user-selected focus areas.
   Aggregate reasoning from LLM.

2. **Holistic Streaming:** Single LLM call, streams entire revised text via SSE.
   Diff computed after stream completes, sent as a structured SSE event.
   No sentence-level streaming (N× cost unacceptable).

3. **New Core Module — `change_engine.py`:** Pure-function diff engine with sentence
   grouping and change classification. No I/O, no LLM calls — deterministic,
   testable, independent.

4. **New Pipeline — `pipeline_coauthor.py`:** Follows existing pipeline pattern
   (`pipeline_rewrite.py`). Constructs `PromptContext` with Co-Author-specific
   variables (focus areas, selection text, context). Streams revised text, then
   computes diff via `change_engine.py`.

5. **New Enum Value — `GenerationMode.CO_AUTHOR`:** Added to existing `_enums.py`.
   Drives prompt selection and context budget allocation.

6. **Per-change Feedback Batching:** Each change gets individual feedback via
   existing `FeedbackService.record()`. Feedback is buffered in the frontend and
   sent as a batch when user clicks "Done" or navigates away. Uses existing
   `context: dict` parameter for change metadata (focus area, change type,
   reasoning). No schema changes to `FeedbackService`.

7. **User-configurable Max Selection Length:** Follows SET-005 pattern — 3-layer
   resolution cascade: user setting → project setting → system default (2000 words).
   No hardcoded limits.

8. **Focus Areas Only:** AI does NOT suggest improvements outside user-selected
   focus areas. The prompt explicitly constrains the LLM to only revise within
   the specified focus dimensions.

### Rationale

1. **Deterministic diff is non-negotiable.** Track-changes UX requires that the
   same original + revised text always produces the same diff. `difflib` is
   deterministic, stdlib, and battle-tested. Option B's structured LLM output is
   inherently non-deterministic.

2. **Plain text is the LLM's strength.** The LLM should focus on writing quality,
   not on producing valid XML. Structured output (Option B) forces the LLM to
   split attention between text quality and format compliance. This reliably
   degrades both.

3. **Single-call streaming is proven.** The rewrite pipeline already demonstrates
   that a single LLM call + SSE streaming works well. Sentence-level streaming
   (Option D) would require N× the cost for marginal UX improvement.

4. **Focus-area scoping controls scope creep.** Without explicit constraint, the
   LLM will "improve" things the user didn't ask for. Focus areas act as a
   semantic boundary on LLM behavior, making the revision predictable and
   controllable.

5. **Feedback batching fits existing infrastructure.** The `FeedbackService`
   already accepts arbitrary `context: dict` metadata. Per-change feedback with
   change-specific context (focus area, change type) requires no schema changes.
   Batching on "Done" avoids N network calls during review.

## Consequences

### Positive

- **Track-changes UX:** Users see exactly what changed, accept/reject individually
- **Deterministic diff:** Same text always produces same diff — testable, debuggable
- **Zero new dependencies:** `difflib` is stdlib, change engine is pure Python
- **Reuses existing infrastructure:** SSE streaming, `connectSSE`, `FeedbackService`,
  `PromptComposer`, `ModelRegistry`
- **Learning feedback:** Per-change accept/reject feeds Rejection Learning (LEARN-001)
- **Focus-area control:** AI only revises within selected dimensions — no scope creep
- **Testable diff engine:** Pure functions with no I/O — unit tests cover all edge cases

### Negative / Tradeoffs

- **No per-change reasoning from LLM:** The LLM provides aggregate reasoning for the
  entire revision. Individual changes get their reasoning inferred from the aggregate
  + focus area. This is a conscious tradeoff for LLM reliability (Option B's per-change
  XML is unreliable).
- **Diff is textual, not semantic:** `difflib` produces word/character-level diffs,
  not semantic changes ("improved dialogue" vs "fixed grammar"). Change types are
  mapped from focus areas, not from the diff itself. This means if a focus area is
  "dialogue", all changes in dialogue passages are labeled "dialogue" regardless of
  the actual change nature.
- **Sentence grouping is heuristic:** Grouping individual diff operations into
  meaningful "change units" (sentences) requires heuristics. Edge cases (fragments,
  run-on sentences, dialogue spanning multiple sentences) may produce suboptimal
  grouping.
- **Aggregate reasoning is less precise:** "I improved the dialogue and made the
  descriptions more vivid" is less helpful than "I changed 'he said angrily' to
  'his voice cracked' because it shows the emotion instead of telling it." This
  tradeoff is accepted because per-change reasoning requires structured output
  (Option B), which was rejected for reliability reasons.

### Risks

| Risk | Mitigation |
|------|------------|
| Diff accuracy degrades for radical rewrites | Prompt constrains LLM to moderate revisions within focus areas. Radical rewrites should use WRITE-004 (Rewrite), not Co-Author. |
| Sentence grouping produces odd change units | Heuristic grouping with configurable thresholds. Frontend can merge/split change units for display. |
| Large selections cause long LLM response times | Max selection length is user-configurable (SET-005 cascade). Default 2000 words keeps response time reasonable. |
| Feedback batching loses data on page navigation | `beforeunload` handler flushes pending feedback. Fallback: accept/reject state persisted in session storage. |
| LLM ignores focus-area constraints and revises outside scope | Prompt engineering + focus-area emphasis in system prompt. Future: few-shot examples per focus area. |

## SSE Event Sequence

The Co-Author endpoint (`POST /api/v1/writing/co-author`) produces the following
SSE event sequence:

```
1. event: request_id
   data: {"request_id": "uuid"}           // Request identifier for tracking

2. event: context_meta
   data: {"kb_characters_count": N, ...}  // Context metadata (same as rewrite)

3. event: text                            // Streamed repeatedly during generation
   data: {"text": "partial revised..."}   // Incremental revised text chunks

4. event: text                            // ... more chunks ...
   data: {"text": "...text continues..."}

5. event: done                            // Generation complete
   data: {"text": "full revised text",    // Complete revised text
          "usage": {...}}                 // Token usage stats

6. event: changes                         // Diff computed post-stream
   data: {"changes": [                    // Classified change groups
     {
       "id": "ch-1",
       "type": "dialogue",              // Derived from focus area
       "original": "he said angrily",
       "revised": "his voice cracked",
       "reasoning": "Show-don't-tell...",
       "position": {"start": 142, "end": 158}
     },
     ...
   ],
   "aggregate_reasoning": "I improved the dialogue..."}  // LLM reasoning

7. event: [DONE]                          // Stream complete
```

**Key design decisions:**
- Steps 1-5 reuse the existing streaming pattern from rewrite mode
- Step 6 (changes) is computed server-side after the full revised text is available
- The `changes` event is the single structured payload — all diff information in one event
- Frontend accumulates text chunks during steps 3-5, then receives the change breakdown
  in step 6 for the review phase

## Implementation Notes

### `change_engine.py` — Pure Function Design

The change engine is a stateless module of pure functions:

```python
import difflib


def compute_diff(original: str, revised: str) -> list[DiffOp]:
    """Compute diff operations between original and revised text."""
    matcher = difflib.SequenceMatcher(None, original, revised)
    ops: list[DiffOp] = []
    pos = 0
    for tag, i1, i2, j1, j2 in matcher.get_opcodes():
        if tag == "equal":
            pos = i2
            continue
        ops.append(DiffOp(
            tag=tag,
            original=original[i1:i2],
            revised=revised[j1:j2],
            position=i1,
        ))
        pos = i2
    return ops
```

### Focus Area → Change Type Mapping

Change types are derived from user-selected focus areas via positional overlap:

1. Each `ChangeGroup` has a position range in the original text
2. The prompt instructs the LLM to annotate revisions with focus-area markers
   (optional — fallback to positional heuristics if absent)
3. If the LLM's aggregate reasoning mentions a focus area, apply it to all changes
4. Fallback: distribute focus areas evenly across changes if no annotation available

### `pipeline_coauthor.py` — Streaming + Diff

Follows the `stream_rewrite()` pattern with two additional steps:

1. **Stream phase:** Stream revised text via SSE (identical to rewrite)
2. **Diff phase:** After stream completes, call `change_engine.compute_diff()`
3. **Emit phase:** Send `changes` SSE event with classified diff

### Feedback Flow

```
User accepts/rejects changes in UI
  → UI buffers feedback entries
  → User clicks "Done" or navigates away
  → Frontend sends batch to POST /api/v1/writing/co-author/feedback
  → CoAuthorService.record_feedback()
    → For each entry: FeedbackService.record(event, context={change metadata})
    → Feedback flows to mem0 (LEARN-001)
```
