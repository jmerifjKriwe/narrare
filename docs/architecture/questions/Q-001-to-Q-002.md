# Q-001 — How does MCP authenticate against the API?

> **Status:** 🟡 Open
> **Blocks:** `apps/mcp/` (post-MVP only)
> **Raised:** project-init
> **Adapter status:** Planned, not implemented. See `docs/features/INDEX.md` → ADAPTER-001.

## Context

When the MCP adapter calls the Service Layer, it needs to authenticate.
The WebUI uses JWT (user logs in, gets a token). MCP clients are not users
in the traditional sense — they are agents acting on behalf of a user.

Options need to be evaluated before MCP implementation begins (post-MVP).

## Options

### Option A — Service account token
A long-lived API key tied to a "system" user. Simple, but no per-user context.

### Option B — User-delegated JWT
User generates an MCP access token in settings. MCP uses this.
Full user context available. Token can be revoked.

### Option C — OAuth-style delegation
MCP client initiates an OAuth flow to get a user-scoped token.
Most correct, most complex to implement.

## Resolution

*Not yet resolved. Needs decision before MCP work begins.*

# Q-002 — Does A2A require streaming support?

> **Status:** 🟡 Open
> **Blocks:** `apps/a2a/` (post-MVP only)
> **Raised:** project-init
> **Adapter status:** Planned, not implemented. See `docs/features/INDEX.md` → ADAPTER-002.

## Context

The LLM Gateway supports both streaming and non-streaming via the same
`stream: bool` parameter. A2A protocol implementations vary — some support
streaming responses, some expect a single complete response.

If A2A requires non-streaming only, we need to ensure all services work
correctly in non-streaming mode (they should, but needs explicit verification).

## Resolution

*Not yet resolved. Post-MVP — low priority until A2A implementation begins.*
