# Q-001 — How does MCP authenticate against the API?

> **Status:** 🟡 Open
> **Blocks:** `apps/mcp/` (post-MVP only)
> **Raised:** project-init

## Context

When the MCP adapter calls the Service Layer, it needs to authenticate.
The WebUI uses JWT (user logs in, gets a token). MCP clients are not users
in the traditional sense — they are agents acting on behalf of a user.

Options need to be evaluated before MCP implementation begins (post-MVP).

## Options

### Option A — Service account token
A long-lived API key tied to a "system" user. Simple, but no per-user context.

### Option B — User-delegated JWT
User generates an MCP access token in settings. MCP uses this.
Full user context available. Token can be revoked.

### Option C — OAuth-style delegation
MCP client initiates an OAuth flow to get a user-scoped token.
Most correct, most complex to implement.

## Resolution

*Not yet resolved. Needs decision before MCP work begins.*

# Q-002 — Does A2A require streaming support?

> **Status:** 🟡 Open
> **Blocks:** `apps/a2a/` (post-MVP only)
> **Raised:** project-init

## Context

The LLM Gateway supports both streaming and non-streaming via the same
`stream: bool` parameter. A2A protocol implementations vary — some support
streaming responses, some expect a single complete response.

If A2A requires non-streaming only, we need to ensure all services work
correctly in non-streaming mode (they should, but needs explicit verification).

## Resolution

*Not yet resolved. Post-MVP — low priority until A2A implementation begins.*

# Q-003 — Embedding provider abstraction from day one?

> **Status:** 🟡 Open
> **Blocks:** `core/llm/embeddings.py` final design
> **Raised:** project-init

## Context

Currently `embeddings.py` uses `text-embedding-3-small` (OpenAI) directly.
This is an approved RULE-01 exception. The question is whether to build a
provider-agnostic embedding interface from the start, or to use OpenAI
and add abstraction later.

Arguments for abstraction now:
- GLM/Z.AI may have an embedding model
- Ollama supports local embeddings
- Changing embedding models later requires re-embedding all existing content

Arguments for OpenAI now, abstract later:
- OpenAI embeddings are the de facto standard
- Abstraction adds complexity before we know what alternatives we'll actually use
- Re-embedding is a one-time migration task, not an ongoing burden

## Resolution

*Not yet resolved. Post-MVP — decision needed when embedding provider diversity becomes a requirement.*

# Q-004 — Celery vs arq for background tasks?

> **Status:** ✅ Resolved
> **Blocks:** ~~`core/tasks/` implementation~~
> **Raised:** project-init

## Context

The tech stack specifies Celery. arq is a newer, async-native alternative
that uses Redis (already in our stack) and has a simpler API.

arq advantages:
- Pure async — no sync/async bridge complexity
- Simpler API — less boilerplate
- Lighter dependency footprint
- Better fit for Python 3.14 async patterns

Celery advantages:
- Battle-tested at scale
- More ecosystem integrations
- Better observability tooling (Flower)
- More familiar to more developers

Background tasks in Narrare are: batch embedding, consistency checks,
chapter summarization, fact extraction. These are medium-complexity tasks,
not high-throughput pipelines.

## Resolution

**Decision: TaskIQ** — Neither Celery nor arq. TaskIQ was chosen as it provides
async-native task execution with Redis backend, aligns with the project's
Python 3.14 async architecture, and offers better developer ergonomics than
both alternatives. See **ADR-007** for full rationale.
