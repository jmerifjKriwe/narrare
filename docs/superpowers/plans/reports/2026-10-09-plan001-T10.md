## Deviations

1. **Task brief vs plan on round-trip semantics**: the brief says "re-upgrade → scenes survive";
   physically impossible with the plan-mandated symmetric drop (data lives only in the dropped
   column). The binding plan text (`op.add_column` / symmetric drop) wins; the test asserts the real
   guarantees — row + all other columns survive both directions, column round-trips structurally,
   snapshot loss documented in the migration docstring (spec §8.2 snapshot is ephemeral request
   state, not durable content).
2. **repository.py + service.py + new modules beyond the plan's file list** (plan listed models /
   0048 / schemas / _helpers only): `_helpers.create_request_row` delegates to
   `repo.create_if_no_active`, so persisting scenes REQUIRES the repo param (repo owns queries —
   bypassing it with a second UPDATE would be a workaround); `build_pipeline_request` had to move
   out of `_helpers.py` (398/400 RULE-04) with `service.py` re-pointed; `schemas_scenes.py` split
   forced by the 200-line config_schema gate. All are RULE-04/RULE-06 modularizations of the plan's
   own interface — no behavior change beyond the plan's.

   branch debt, not T10: `test_prompt_path_adoption.py` expected 44 registry modes while T7's

   the count 44→46 with the file's own documented ratchet procedure ("When adding a mode, update
