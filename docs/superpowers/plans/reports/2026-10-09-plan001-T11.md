## Deviations

1. **Scene types not re-exported from the `@/types` barrel yet** (deferred to T13).
   The plan's T11 file list names exactly 3 production files; `types/index.ts` is a
   4th file and the ≤3-file cap is binding. House convention imports types from the
   `@/types` barrel, so `lib/api/planning.ts` / `lib/hooks/usePlanning.ts` import the
   new scene types directly from `@/types/planning` (pattern endorsed by
   `lib/api/client.ts` "import directly from domain files"; planning is already absent
   from the `lib/api` barrel). T12 consumers should import from `@/types/planning`
   until T13c — which already touches `types/index.ts` for the `OutlineBeat` removal —
   adds the scene re-exports (or the coordinator re-slices).
2. **Draft/refine request fields are optional (`?`)** where the BE schema carries
   defaults (`structure_type=""`, `scene_count=0`, …) — mirrors the existing
   `OutlineUpdateRequest` convention (BE-defaulted ⟷ FE-optional); field NAMES are
   exact. Response fields stay required (`ai_unavailable: boolean`,
   `proposal: SceneProposal | null`). Rule-17 is about names; optionality follows
   server defaults so T12/T13 call sites can send partial instructions.
3. **Hook signatures follow plan T11, not the spec §9 sketch**: spec §9 sketches
   `useDraftScenes(novelId, chapterId)` / `useRefineScene(...)`, plan T11 (binding
   task interface) specifies `useDraftScenes(novelId)` / `useRefineScene(novelId)` —
   absorbed at plan time, plan wins. `chapterId` travels in the mutation variables
   (`{ chapterId, body }`), mirroring `useSaveScenePlans`; functionally equivalent
   (zero-write generators, no invalidation).
