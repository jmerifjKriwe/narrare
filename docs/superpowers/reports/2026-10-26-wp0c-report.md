## What landed

- **The lane owns progress** (`kernel/jobs`): handlers report through a callback; the
  worker persists it in its own transaction, gated on the claim still being `RUNNING`.
  A failing handler's last reported value survives, and D3 (a failed job writes no audit
  row) is untouched.
- **`ask_structured`** (capability-local): schema-bound ask, `json_repair` before the
  one retry that carries the validation error, then `MalformedAnswerError` whose text is
  the parse reason — the same text the lane writes to `Job.error`.
- **Extraction bound**: 20 000 characters (not bytes, inclusive), the prompt cut, the
  result carries `truncated`, the dock names it.
- **Chapter groups**: chapters packed under the same bound, one pass per group, findings
  merged and deduplicated by `summary`, progress per group and reset to 0 at the start of
  a run, oversized chapters skipped by `{position, title}` and named in the dock with the
  rail's own default label when the stored title is empty.

## Deviations

1. **Progress is written by the lane, not the handler** — design decision, recorded there.
2. **`json_repair` is a new runtime dependency** — approved by the product owner against
   the recommendation to stay dependency-free.
3. **A chapterless novel makes no provider call** where it used to receive an empty prompt.
4. **Chapters are grouped, not sent one per pass** (found while implementing Task 4).
   §3.2 asks for "one pass per chapter"; a per-chapter pass cannot detect a contradiction
   *between* two chapters, and the canon holds names and kinds, not the other text. Groups
   keep the check's product promise; the group boundary is where detection stops. Two
   short chapters still make one pass, which is exactly what the check did before.
5. **The malformed-JSON path is proven at the provider boundary in unit tests, not in an
   E2E against a scripted openai-compatible stand-in.** The plan named the stand-in as one
   option; building a second SSE vendor in `kernel/testing` for one path was judged more
   test surface than the proof adds, because the adapter's `response_format` mapping is
   already unit-tested (`kernel/tests/test_openai_compat.py`) and the retry logic is
   boundary-local. If the reviewer disagrees, this is the cheapest place to add it.
6. **Result-shape assertions changed** in four existing tests (extraction result gains
   `truncated`, consistency result gains `skipped_chapters`, two restart E2Es) — a
   consequence the plan's tasks imply but do not name.

## PR review (CodeRabbit, after the push)

Two findings, both verified against the code and both real:

1. **Major — the schemas had an array root.** Structured outputs (the OpenAI contract the
   adapter speaks) requires the root to be an **object**; an array root is refused
   outright, so every call of this branch would have failed against a real endpoint with
   a 400. Fixed: both schemas carry `{"items": [...]}` under an object root, the parsers
   unwrap it and refuse a bare array as the contract violation it now is, and the fake
   answers in the same shape so the dev path and the real path cannot drift apart.
2. **Minor — a dead progress write failed the job.** The write sits in the lane's own
   transaction, so its exception reached the handler path: finished work was rolled back
   and the lane earned a second provider run. Progress is advisory; the write now logs
   and continues, cancellation still propagates. A kernel test pins it with a broken
   session factory.

Result-shape assertions moved with the object root (the fake's own tests, the two parse
refusal tests, the scripted providers) — a consequence, not a new contract.
